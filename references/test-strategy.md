# 测试策略与覆盖率治理（Test Strategy & Coverage Governance）

> 设计测试策略：测试金字塔比例、覆盖率目标分级、CI 质量门禁、测试债管理。面向「该写什么测试、写到什么程度、如何在 CI 卡质量」。

## 何时使用

- 用户说「为项目设计测试策略」「配置 CI 覆盖率门禁」「清理测试债」「这个模块该写什么测试」
- 需要拍板测试投入分配、覆盖率阈值、回归策略

## 测试金字塔

```
        /\
       /E2E\       ~10%  关键业务链路、跨页面流程
      /------\
     /集成测试\     ~20%  模块间协作、数据库、消息
    /----------\
   /  单元测试   \  ~70%  函数/类、纯逻辑、边界
  /--------------\
```

- 倒金字塔（E2E 过多）是反模式：慢、脆、贵。
- 比例可按风险调整：核心支付链路可加厚 E2E。

## 覆盖率目标分级

不要一刀切 100%：

| 模块类型 | 行覆盖 | 分支覆盖 |
|----------|--------|----------|
| 核心逻辑（支付/权限/算法） | ≥ 90% | ≥ 85% |
| 一般业务 | ≥ 80% | ≥ 70% |
| 胶水/适配层 | ≥ 60% | — |

- 行覆盖 ≠ 分支覆盖；关键模块盯分支覆盖。
- 覆盖率达标 ≠ 无 bug：需用边界/异常/性能用例补足。

## CI 质量门禁

- **覆盖率门槛**：PR 合并前覆盖率不下降，且核心模块达标。
- **趋势追踪**：记录覆盖率历史，回退即告警。
- **必过检查**：单测 + lint + 类型检查 + 关键 E2E 作为 merge gate。

参考 `assets/ci-coverage.yml` 获取可直接套用的 GitHub Actions 门禁配置（含覆盖率上传与门槛）。

## 测试债管理

- 识别长期未更新、长期全绿无变化的测试（可能已失效）。
- 识别误报率高（flaky）的测试，优先修或隔离。
- 删除/重写与实现脱节的测试，避免「绿但假」。
- 对无测试的核心模块排期补测，纳入迭代。

## 测试类型选择

| 需求 | 选 |
|------|----|
| 验证纯逻辑 | 单元测试 |
| 验证多模块协作 | 集成测试 |
| 验证用户流程 | E2E |
| 验证接口契约 | 契约测试（见 `references/contract-testing.md`） |
| 防 UI 回归 | 可视化回归（见 `references/visual-regression.md`） |
| 防性能退化 | 性能测试（见 `references/performance-testing.md`） |
| 防安全漏洞 | 安全测试（见 `references/security-testing.md`） |

## 限制

- 策略需结合项目类型/团队规模调整，本 playbook 给方法论不替你拍板。
- 不涉及具体框架的逐行配置（见各专项 references 与 assets 模板）。
